# Agent 工程 · Tool calling 协议（第 1 讲）

> 导航：[目录](./README.md) · 上一讲：[00 · 概念地图](./00-概念地图.md) · 下一讲：待更新（Agent loop）


## 这一讲解决什么

搞清一件事：模型**不能直接执行代码**，它只能发出「我想调哪个工具、参数是什么」；真正跑工具的是你的**运行时**。

这套约定就叫 **Tool calling（工具调用 / Function calling）协议**。

## 和「普通函数」的差别

| | 普通函数调用 | Tool calling |
|--|-------------|--------------|
| 谁决定调用 | 你的代码写死 / 条件分支 | **模型**根据对话决定 |
| 参数从哪来 | 你传入 | 模型生成（常是 JSON 字符串） |
| 谁执行 | 解释器 / 引擎 | **你的运行时**解析后执行 |
| 返回给谁 | 调用方变量 | 再塞回对话，给模型当「观察」 |

前端类比：模型像前端点了「请求」，OpenAPI/路由像工具定义，后端 handler 像工具实现。

## 协议里的三种角色（消息）

1. **`assistant` + `tool_calls`**：模型说「请调这些工具」
2. **`tool`**：运行时把执行结果贴回去（带上对应的 `tool_call_id`）
3. **再次 `assistant`**：模型根据结果继续调工具，或给出最终自然语言回答

没有 `tool` 回执，模型就看不到真实世界发生了什么。

## 一次调用长什么样（结构）

模型侧（示意）：

```json
{
  "role": "assistant",
  "tool_calls": [
    {
      "id": "call_1",
      "type": "function",
      "function": {
        "name": "get_weather",
        "arguments": "{\"city\":\"上海\",\"date\":\"2026-09-11\"}"
      }
    }
  ]
}
```

运行时侧回执（示意）：

```json
{
  "role": "tool",
  "tool_call_id": "call_1",
  "content": "{\"temp_c\":28,\"precip_prob\":0.6}"
}
```

### 字段分工（务必分清）

| 字段 | 谁填 | 含义 |
|------|------|------|
| `function.name` | 模型 | 调哪个工具 |
| `function.arguments` | 模型 | 参数（通常是 JSON **字符串**） |
| `tool_calls[].id` | 多为 API/运行时 | 这次调用的编号 |
| `role` | 运行时/框架 | 消息身份 |
| `tool` 的 `content` | 运行时 | 工具真实输出 |
| `tool_call_id` | 运行时 | 把结果对回某次调用 |

## 工具要先「登记」：Schema

调用前，你要把可用工具的说明书交给模型，常见形态：

- 工具名（稳定、可读）
- 一段描述（模型靠描述决定何时用）
- 参数 JSON Schema（类型、必填、枚举）

没有清晰 schema，模型容易瞎编参数名或漏必填项。

## 运行时最小职责清单

1. 把系统提示 + 历史消息 + **工具定义**发给模型  
2. 若返回含 `tool_calls`：校验 → 执行 → 组装 `tool` 消息  
3. 把 `tool` 消息追加进上下文，再调模型  
4. 直到模型给出最终文本回答（或触发你的停止条件）

这就是单步 tool calling；多步重复 2–3，就接近 Agent loop（第 2 讲会展开）。

## 并行调用（了解即可）

有的接口允许一次返回**多个** `tool_calls`（互不依赖时可并行执行）。  
依赖关系强时（先查天气再建议穿衣），应串行：先拿 observation，再让模型决定下一步。

## 常见坑

- 把工具结果写成给人看的长散文，下一步难复用 → 优先**结构化**返回  
- `arguments` 不是合法 JSON → 运行时要校验/重试策略  
- 忘了回传 `tool` 消息，却指望模型「知道」已执行  
- 工具描述含糊，模型乱选或乱填参  
- 把「最终对用户说话」和「调工具」混在同一步却不处理停条件
