# Agent 工程 · 记忆与上下文（第 3 讲）

> 导航：[目录](./README.md) · 上一讲：[02 · Agent loop](./02-Agent-loop.md) · 下一讲：[04 · 评测与工程化](./04-评测与工程化.md)

## 这一讲解决什么

第 2 讲里，消息会在 loop 中不断堆积。  
第 3 讲回答：**哪些东西该进上下文、哪些该持久化成「记忆」，以及和 RAG 怎么分界。**

一句话：上下文是「这一局桌上摊开的牌」；记忆是「你可以之后再抽的牌库」。

## 先分清三个词

| 概念 | 是什么 | 生命周期 |
|------|--------|----------|
| **上下文（Context）** | 某次请求里塞给模型的 messages / 系统提示 | 通常随一次调用或一轮会话 |
| **短时记忆** | 当前任务还要用的状态（目标、已查结果、用户偏好） | 会话内；可写进 messages 或会话 store |
| **长时记忆** | 跨会话仍有用的事实（用户偏好、项目约定） | 持久存储；需要时再取回塞进上下文 |

模型本身**没有**可靠的跨请求硬盘——「记得」全靠你的运行时怎么存、怎么取、怎么塞。

## 上下文窗口：硬约束

模型有 **context window**（可吃下的 token 上限）。超出则：截断、报错、或质量崩盘。

工程含义：

- 不是「历史越全越好」，而是「**与当前决策相关的**尽量全」  
- Agent 轨迹（大量 tool 回执）最容易把窗口撑爆  
- 所以要有裁剪 / 摘要 / 外置存储策略（第 2 讲提过，这里展开）

## 常见记忆分层（实用模型）

1. **工作记忆（Working）**  
   当前目标、计划、本轮关键 observation。几乎总在上下文里。

2. **会话记忆（Session）**  
   同一 chat 的摘要、用户本会话说过的约束。会话结束可丢或归档。

3. **长期记忆（Long-term）**  
   用户画像、项目规范、历史结论。存在 DB / 文件 / 向量库；**按需检索**后再写入上下文。

4. **工具侧状态（World state）**  
   真正的业务真相在数据库、文件系统、工单系统——不要全靠模型「记住」。

前端类比：Redux/组件 state ≈ 工作记忆；`localStorage`/账号资料 ≈ 长期记忆；后端 DB ≈ world state。

## 和 RAG 的边界

| | 记忆 | RAG |
|--|------|-----|
| 典型内容 | 「关于这个用户/任务」的状态与约定 | 「关于某个知识库」的文档片段 |
| 写入 | Agent/产品逻辑主动写入 | 文档索引流水线为主 |
| 读取 | 按会话/用户键取，或轻量检索 | 向量/关键词检索 top-k |
| 风险 | 写错会污染以后所有对话 | 检索不准会答非所问 |

口诀：

- **个性化、状态、约定** → 记忆  
- **大文档、政策、知识库** → RAG  
- 两者都可能「检索后塞进上下文」，但**数据从哪来、谁维护**不同

不是所有 Agent 都需要向量库；很多产品有「会话摘要 + 用户偏好表」就够。

## 写入与读取原则

**该写长时记忆时**

- 用户明确说「记住这个」  
- 稳定偏好（语言、时区、风格）  
- 可验证的项目事实（经确认的）

**不该乱写时**

- 一次性临时信息  
- 未确认的猜测  
- 敏感密钥（应走密钥管理，不进记忆文本）

**读回上下文时**

- 只注入**当前问题需要的**几条  
- 标明来源（「来自用户资料」），减少模型幻觉成「刚聊过」  
- 与系统提示、工具定义一起占窗口预算——要记账

## 会话内：轨迹怎么压缩

Agent loop 跑多了，优先考虑：

1. **保留**：系统提示、用户目标、最近 N 轮、未完成计划  
2. **折叠**：早期成功的 tool 结果 → 一行结论  
3. **外置**：大段 JSON 存对象存储，上下文里只留指针/摘要  
4. **摘要模型**：周期性把轨迹压成「状态卡片」再替换旧消息

目标：让下一步决策仍够用，而不是复读全部历史。

- 第 3 讲：用分层记忆 + 裁剪/摘要 +（可选）RAG，把上下文变成可控资源
