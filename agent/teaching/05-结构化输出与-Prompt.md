# Agent 工程 · 结构化输出与 Prompt（第 5 讲）

> 导航：[目录](./README.md) · 上一讲：[04 · 评测与工程化](./04-评测与工程化.md) · 下一讲：[06 · 多 Agent 与编排](./06-多-Agent-与编排.md)

## 这一讲解决什么

Agent 要**可接代码**，不能只靠散文。  
讲清：**结构化输出**、**工具参数 JSON**、以及面向 Agent 的 Prompt 怎么写。

## 为什么结构化重要

| 散文输出 | 结构化输出 |
|----------|------------|
| 人好看，机器难用 | 可校验、可断言、可接下一跳 |
| 评测靠「感觉」 | 可对字段做自动判 |
| 易夹带幻觉数字 | schema 约束类型与必填 |

Tool calling 的 `arguments` 本质上就是在逼模型「填表」。

## 三条输出通道

1. **给用户看的自然语言**（最终回答）  
2. **给运行时的 tool arguments**（JSON 字符串）  
3. **给下游的结构化对象**（JSON Schema / 受限解码）

设计时先问：这一步的消费者是人、是工具、还是另一个服务？

## Schema 怎么写才有用

- 字段名稳定、语义单一  
- 必填 / 可选分清；枚举写死  
- 描述写「何时用、勿何时用」  
- 避免一个大字符串塞所有信息

坏例子：`data: string` 里塞整篇报告。  
好例子：拆成 `temp_c`、`precip_prob`、`summary`。

## Prompt（Agent 向）要点

系统提示通常要写清：

1. **角色与目标**（你要完成什么）  
2. **工具使用规则**（先查再答；禁止臆造实时数据）  
3. **停止与澄清**（信息不够就问用户）  
4. **输出格式**（最终怎么对用户说；何时只调工具不闲聊）  
5. **安全边界**（见第 7 讲，这里先占位）

少而硬的规则，优于一堆形容词。

## 常见手法

- **先计划后执行**：允许短计划，但要防空谈不调工具  
- **ReAct 风格**：Thought / Action / Observation（也可内化进 tool loop，不必字面输出 Thought）  
- **校验—重试**：arguments 非法时，把错误当 observation 回灌  
- **双阶段**：模型出草稿 JSON → 本地校验 → 再生成用户文案
