## 这一讲解决什么

单 Agent 不够用时：要不要拆成多个 Agent？和**固定工作流**怎么选？

一句话：**能用一个 Agent + 清晰工具解决的，别上多 Agent。**

## 三种架构对照

| 形态 | 谁决定下一步 | 适合 |
|------|--------------|------|
| **单 Agent + 工具** | 一个模型 loop | 目标开放但领域集中 |
| **多 Agent** | 多个角色模型协作（路由/交接） | 角色差异大、提示词互相干扰 |
| **固定编排 / 工作流** | 你画好的图（可含 Agent 节点） | 合规、审计、强顺序 |

## 什么时候才拆多 Agent

值得拆：

- 提示词互相打架（研究员 vs 写手 vs 审查）  
- 权限不同（只读检索 vs 可写生产）  
- 要并行专长（翻译 + 审校）

不值得拆：

- 只是步骤多 → 先优化工具与 loop  
- 「听起来更 AI」→ 复杂度税很高

## 常见模式（了解名字即可）

1. **Router（路由）**：先分类，再交给专用 Agent  
2. **Supervisor（主管）**：主管拆任务、收结果、再分配  
3. **Pipeline（流水线）**：A 出结构化中间态 → B 消费（更像工作流）  
4. **Debate / Reviewer**：生成后再由审查 Agent 挑错（成本高，用于高风险）

交接时传**结构化状态**，不要只传一大段聊天记录。

## 编排引擎的位置

LangGraph / 自研状态机 / 队列工作流等：

- 负责：状态、边、重试、人工审批节点、持久化  
- Agent 负责：某一节点内的「动态决策」

心智模型：编排是骨骼，Agent 是关节上的肌肉。

## 成本与失败面

多 Agent ≈ 多次模型调用叠加：

- 延迟与费用上升  
- 交接丢失上下文  
- 循环推诿（A 以为 B 会做）

必须有：全局步数/预算、清晰责任边界、可观测的交接日志。
