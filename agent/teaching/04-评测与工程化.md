# Agent 工程 · 评测与工程化（第 4 讲）

> 导航：[目录](./README.md) · 上一讲：[03 · 记忆与上下文](./03-记忆与上下文.md) · 下一讲：[05 · 结构化输出与 Prompt](./05-结构化输出与-Prompt.md)

## 这一讲解决什么

Agent「感觉挺准」不够。工程上要回答：**怎么测、测什么、如何版本化、成本和延迟怎么管。**

一句话：没有评测的 Agent，只是 demo。

## 评测对象不只是「最终一句答对」

至少分三层：

| 层 | 看什么 | 例子 |
|----|--------|------|
| **结果** | 最终对用户是否正确/有用 | 穿衣建议是否合理 |
| **轨迹** | 工具选对了吗、步数是否失控 | 有没有乱调无关工具 |
| **系统** | 延迟、费用、错误率、超时 | p95 延迟、$/任务 |

前端类比：不只测 UI 文案，还要测请求是否打对 API、有没有多余请求。

## 黄金集（Golden set）

准备一组**固定用例**：输入 + 期望（可自动判或人工标）。

好用例特征：

- 覆盖主路径 + 边界（缺参数、工具失败、多步依赖）
- 期望尽量**可判定**（结构化字段、是否调用某工具、是否包含关键事实）
- 版本化进仓库，改 prompt/工具时回归

起步规模：10～30 条就比 0 条强；再慢慢加。

## 自动判 vs 人工判

- **规则 / 断言**：是否调用了 `get_weather`、JSON 字段存在、禁止编造温度  
- **模型当裁判**：适合开放文本（要固定裁判提示词，并抽查校准）  
- **人工抽检**：高风险场景必留

常见指标：pass rate、工具调用正确率、平均步数、失败类型分布。

## 轨迹日志（必须打）

每次任务至少记下：

- 输入、最终输出  
- 每步：模型决定、tool 名/参数、回执摘要、耗时  
- token、费用估算、停止原因（正常 / 触顶 / 熔断）

没有轨迹，线上问题只能猜。注意脱敏（密钥、隐私）。

## Prompt / 工具 / 模型的版本管理

把会改变行为的东西当「配置发布」：

- prompt 文本、工具 schema、模型名与参数  
- 与黄金集结果一起记：哪一版 pass rate 多少  
- 回滚能力：坏版本能切回去

不要只在聊天窗口里改一句「好像更好」。

## 成本与延迟

Agent 多轮 = 多次模型调用 + 工具等待。

手段：

- 能规则做的别叫模型  
- 并行互不依赖的 tool_calls  
- 控制最大步数与上下文体积（见第 2、3 讲）  
- 缓存稳定工具结果（短 TTL）

产品上要有预算意识：每个任务的「可接受 $/延迟」。
